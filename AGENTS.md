# Omen Flow agent instructions

## Product UI and design

Before creating or changing any user-facing surface, read [the Lens design specification](design-system/design.md). Use [the canonical tokens](design-system/tokens.css) (semantic roles in both themes, never raw values), vendored fonts, the brand mark (`Mark` / `design-system/brand/`), and the primitives in `apps/desktop/src/renderer/ui/kit.tsx` (`Button`, `IconButton`, `Tooltip`, `ConfirmButton`, `Menu`, `Segmented`, `Field`, `Checkbox`, `QuantityField`, `State`, `Notice`, `Empty`, `Skeleton`, `Qty`, `Time`, …; `ErrorBoundary` in `ui/ErrorBoundary.tsx`). The live **Design system** view (`renderer/system/DesignSystemView.tsx`) is the component reference.

Preserve the Lens interaction model: three zoom levels (the project through one lens — Flow, Parts, Timeline, Files, Evidence → one object between its input and consequence rails → one decision), a left activity bar (Agent tab first), no dashboard, causal left-to-right layout, type-shaped stages, and the agent surface (tab and floating window, session bar, activity rail from the host's call ledger) with two panes: the conversation (headless Codex or Claude Code runs with inline cards; `renderer/chat/`, `styles/conversation.css`, host side `crates/agent-host/src/chat.rs`) and the terminal wired to the real PTY. One agent works in a project at a time, and “Ask agent” follows the active pane. Keep the visual language: graphite field, islands for floating controls, Geist interface text, IBM Plex Mono values, Phosphor icons, one signal accent reserved for live and focused things, and labelled engineering state. Add a stage or a lens rather than a page: a lens is one entry in the `LENSES` registry (`renderer/project/lenses.ts`) plus its component, and the activity bar, `⌘n`, the omnibar, the preview and the catalogue read that list. Styles live in `renderer/styles/`, one file per surface, imported in cascade order by `styles/index.css`; put a rule in the file of the surface it styles. Follow the specification’s extension checklist and update the catalogue for new reusable patterns.

Preserve quantities and units, unknowns, evidence, revision history, and human review. Do not fabricate tool success, agent activity, collaboration, production readiness, or data. Keep existing `@omenflow` APIs, `omenflow call` / `omenflow mcp`, and `.omenflow` storage (schema 1, additive changes only) compatible unless the task explicitly includes migration. Contracts change first in `packages/contracts` and are exported with `pnpm contracts:export`; see [CONTRIBUTING.md](CONTRIBUTING.md).

Use `pnpm design:preview` for disposable populated design review: it runs the real renderer on the Rust headless host (`apps/headless`, `omenflow-host`) with the rover and drone fixtures, and its Agent tab runs a real terminal and real conversation sends (a Custom CLI; Codex CLI and Claude Code only with `OMEN_PREVIEW_AGENTS=1`, since they spend model credits and may update themselves; without it, terminals and conversation sends are refused). Use `pnpm dev` for native desktop validation. See `design-system/verification.md` for the latest checks and limits.

## Videos

`videos/` is a standalone npm package (not a pnpm workspace member) holding the launch trailer. `videos/trailer/` is a deterministic HTML composition: `render(t)` sets every property from time alone, using the canonical tokens, fonts, mark, Phosphor icons and Sable rover fixture data. Run `npm install` in `videos/`, then `npm run preview` (scrubbable, space to play) or `npm run render` (needs Homebrew `ffmpeg`; writes `videos/omen-flow-trailer.mp4`). `node scripts/render.mjs --draft` renders a quick 30 fps version to `out/`, and `--still 5.6,9.1 --still-dir /tmp/x` exports PNG frames for review. The soundtrack is synthesised by `scripts/audio.mjs` from the same timeline, so keep cue times in step when retiming scenes. The root `.prettierignore` excludes `videos/`; it keeps its own formatting.
